# Noir Rebrand and Registration Reliability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make registration work reliably at `127.0.0.1:8000`, show actionable validation errors, and rebrand all user-facing IDA/MailFlow surfaces to Noir with a restrained Night Moss visual system.

**Architecture:** Keep internal Django app names, Python imports, URLs, and database tables unchanged. Fix registration at the template/middleware/request boundary, add regression coverage for both valid and CSRF-protected POSTs, then centralize user-facing brand name and palette values in shared templates/static CSS so the rebrand is consistent without risky broad renames.

**Tech Stack:** Django 6, Django templates, Django test client, WhiteNoise/staticfiles, existing CSS and template inheritance.

---

- Inspect: `apps/accounts/templates/auth/register.html`
- Inspect: `apps/accounts/views.py`
- Inspect: `core/settings.py`

- [ ] **Step 1: Add a failing browser-equivalent regression test**

Add a test that GETs the registration page, extracts the rendered CSRF token, and submits the exact visible form fields with the test client. Assert the response is a redirect and the account exists.

- [ ] **Step 2: Run the focused test and confirm the failure**

Run:

```bash
./venv/bin/python manage.py test apps.accounts.tests.AuthFlowTests.test_register_browser_submission
```

Expected before the fix: failure showing a 403 CSRF response or a non-redirect response, proving the test exercises the reported boundary.

- [ ] **Step 3: Inspect the rendered response**

Confirm the form contains a hidden `csrfmiddlewaretoken`, the CSRF cookie is set on GET, and the form action is same-origin. If any of these are absent, fix only the missing boundary.

- [ ] **Step 4: Commit the reproduction test**

```bash

```

### Task 2: Fix registration CSRF handling and error visibility

**Files:**
- Modify: `apps/accounts/templates/auth/register.html`
- Modify: `apps/accounts/views.py` only if the evidence shows request handling is the source
- Modify: `core/settings.py` only if trusted origins/cookie settings are required for the local host
- Test: `apps/accounts/tests.py`

- [ ] **Step 1: Make the rendered form robust**

Keep `{% csrf_token %}` directly inside the registration form, preserve the same-origin URL generated by `{% url 'accounts:register' %}`, and ensure the submit button does not disable or remove the form/token before native submission.

- [ ] **Step 2: Render all server-side form errors clearly**

Display non-field and field errors for every required field, including `first_name` and `last_name`, so an invalid POST cannot look like a silent reload.

- [ ] **Step 3: Add CSRF and invalid-form assertions**

Cover:

```python
response = self.client.post(reverse("accounts:register"), data, follow=False)
self.assertEqual(response.status_code, 302)

invalid = self.client.post(reverse("accounts:register"), data_without_required_field)
self.assertEqual(invalid.status_code, 200)
self.assertContains(invalid, "This field is required.")
```

Also verify a CSRF-enforced client receives 403 without a token and succeeds with the rendered token.

- [ ] **Step 4: Run registration tests**

```bash
./venv/bin/python manage.py test apps.accounts --verbosity 1
```

Expected: all authentication tests pass and valid registration redirects to the dashboard.

- [ ] **Step 5: Commit the registration fix**

```bash
git add apps/accounts/templates/auth/register.html apps/accounts/views.py core/settings.py apps/accounts/tests.py
git commit -m "fix: make registration CSRF-safe and debuggable"
```
